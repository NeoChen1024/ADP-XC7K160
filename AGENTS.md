# ADP-XC7K160 board notes — Agent guide

This repository is a record of one Andes AndeShape ADP-XC7K160 board. The deliverable is the
record: a different project must be able to use the board from it. The designs and the scripts
exist to measure the board and to verify the record.

The repository is public. The board, its flash contents and the LAN that it connects to belong to
the owner.

## Sources of truth

- [README.md](README.md) gives the overview: the evidence marks, a summary of each part of the
  board with a link, the file list and the quick start.
- `docs/` owns the description of the board, one file for each part. `docs/unknowns.md` lists
  what is not known.
- `workbench/README.md` describes the workbench. `litex/README.md` describes the LiteX SoC, and
  `litex/linux/README.md` describes Linux and Debian on it.
- `pins.csv` and `package-pins.csv` are generated. `tools/tables.py` makes them from
  `tools/manual-pins.csv` and `tools/package-dump.csv`. Do not edit the two tables by hand. A
  finding about a pin goes into the `board` set and the `notes` of `tools/tables.py`; then make the
  tables again.
- `adp_xc7k160_master.xdc` has no generator in this repository. Edit it by hand, and keep it in
  agreement with `pins.csv`.
- `mig/prj/*.prj` are generated by `mig/mig_prj.py`. Change the script, then make the files again.
- [LICENSE](LICENSE) owns the licensing terms: the MIT License for all files.
- `workbench/board.py` owns the channel table of the workbench. The build makes
  `workbench_pkg.sv` and `pins.xdc` from it, and `workbench.py` reads the same table.
- The start of `workbench/rtl/adp_xc7k160_workbench.sv` owns the command protocol.
- `litex/adp_xc7k160_platform.py` reads its pins from `pins.csv`. Do not write a pin number into it.
- `litex/versions.txt` is made by `litex/versions.sh`. It names the LiteX commits of the result in
  `litex/README.md`. Make it again when a new result uses a different installation.
- `workbench/results/` holds the records of measurements, with the date in each file name.
- `workbench/prebuilt/` holds the bitstreams and the reports of one build.
- The start of each script owns its usage and options.

Keep this guide about workflow. If a fact about the board changes, change the file of `docs/`
that owns it, and the summary in the README if it changes. Link to the documents from here; do not
copy pins, figures or limits into this guide.

## Evidence marks

- Each statement about the board has a source: `[measured]`, `[package]` or `[manual]`. The README
  defines them. If there is no source, the text says that the fact is not known.
- Write `[measured]` only for something that ran on this board or that an instrument showed. A
  statement that seems reasonable stays `[manual]`, or goes into `docs/unknowns.md`.
- A person can also be the source: a marking that was read, a switch position that was seen. Say
  so ("seen", "the marking").
- If a measurement contradicts the manual or an earlier statement, keep a short note of what was
  wrong. Do not delete it silently.
- A change that answers or raises a question updates `docs/unknowns.md` in the same edit.
- The documents, the script comments and `pins.csv` refer to the documents by their file names.
  After you rename, remove or split a document, check each reference to it.

## Documents

- A document describes the present state: what the board is, what the designs do, and the results
  that support them. It is not a log of the work.
- Remove the steps of past work, the old states and the old figures when they no longer apply. Git
  keeps them. Keep a short note only where an earlier statement was wrong (see above).
- A table of builds or measurements keeps the present build, and the other rows only if a statement
  of the document uses them.

## Numbers and claims

- A measured figure says how it was measured: the command or the design, the bitstream (pull-up or
  pull-down), the date and the count.
- Never write a plausible value. Do not carry a figure from an earlier build as if it were current.
  LUT counts, flip-flop counts and slack come from the reports in `workbench/prebuilt/` or from the
  build that the text names.
- A result for one chip, one card or one temperature says so. It is not a guarantee.
- A statement about a part (a PHY, a codec, a reset supervisor, a memory) says where it comes from:
  the datasheet that was read, the marking, or a measurement. Name the document.
- An estimate of a tool (for example `report_power`) is called an estimate.

## Board safety

- Write the configuration flash U4 only when the owner explicitly asks for that write. Only then
  run `jtag/flash_u4.sh`. No other tool in this repository writes U4. A design that does not use
  U4 holds `FCS_B`, `FOE_B` and `FWE_B` high.
- The U17 probe (`flash-probes/u17`) passes each command to the flash. Its `dump.py` sends only
  read commands. Keep it so.
- Write the user flash U17 only when the owner asks, each time. A JTAG load of the FPGA does not
  need this: it is gone at power-off.
- The I2C EEPROM is only read.
- The workbench reads a pin with an unknown connection and never drives it. It drives only the
  lines that the board gives to the FPGA to drive. It does not drive the pins of bank 16.
- Do not put `PULLUP` on the pins of the Ethernet PHY (`docs/ethernet.md`).
- `workbench.py net` and `workbench.py sdrw` are the only commands with an effect outside the
  board. They are not part of `auto`. Run them only when the owner permits it in that session.
  `net` sends only to the host that runs it, and to the ARP broadcast address.
- The LiteX SoC with `--with-etherbone` answers on the LAN. Load it only when the owner permits
  it in that session. Its IP address is a build option and does not go into the repository.
- The LiteX SoC writes the SD card only when it is built with `--with-sdcard-write`. Use that
  option only with a card that the owner gave for writing. On 2026-11-21 the owner gave the card
  that is now in the socket for the Debian work: it can be written, and its old contents need no
  copy. Any other card needs the owner's permission.
- A new command that sends to a network or writes to a medium follows the same pattern: it is
  explicit, it is not part of `auto`, and its document gives its limits.
- A test that overwrites data first stores the original data in a file. It deletes the file only
  after it has restored and verified the data. A step that injects a fault goes last.
- Connect or disconnect the JTAG cable only while the board has no power.

## Publication and privacy

- Do not put these into a file of the repository: a host name, a user name, a home directory path,
  an IP address or a MAC address of the LAN. Write a path as `/path/to/...`.
- Filter a result file before you store it. `workbench/results/net-2026-11-20.txt` is an example:
  the lines with the addresses of the host and of the board were removed.
- A Vivado report has a `Host` line. Remove the host name before the report goes into `prebuilt/`.
- The MAC address in `workbench.py` is locally administered and is not a real address.

## Third-party material

- The manual (UM098) is a document of Andes. Do not put the PDF, its text or its figures into the
  repository. State a pin assignment as a fact and cite the section. A short quotation with its
  source is the limit.
- The contents of U4 are software of Andes. The flash backups do not go into the repository, and
  an image that `flash-probes/` reads does not either.
- Do not commit the output of MIG or other generated Xilinx IP. The repository has the `.prj` files
  and the scripts that generate it.
- Refer to a third-party tool by its URL and commit (for example xvc-pico). Do not copy its code.
- Describe a datasheet in your own words and name it.

## Designs and scripts

- A build writes its products outside the repository: to the current directory, or to `WORK`. Do
  not leave build output or `__pycache__` in the repository. The Python scripts set
  `sys.dont_write_bytecode`.
- Vivado writes a bitstream when timing fails. The `build.sh` scripts and `flash-probes/run.sh`
  check the slack; a new build script must do the same.
- Simulate a change to the workbench with `workbench/sim/run.sh` before you build it.
- A change to the command protocol changes `MAGIC` in `workbench/board.py`. Change the protocol
  text in the RTL, the testbench and `workbench.py` in the same edit.
- Replace the files of `workbench/prebuilt/` together: both bitstreams and all reports come from
  one build. Then update the figures in `workbench/README.md`.
- Do not change an old file in `workbench/results/`. A new measurement is a new file with its
  date. If a new result replaces an old one, the documents refer to the new file.
- The files in `workbench/probes/` are one-time scripts, kept so that the work can be done again.
  If a probe needs an earlier design, its first lines say so.
- The Python scripts use the standard library and pyserial. A new dependency needs a reason.
  The scripts of `litex/` also need LiteX, because they are LiteX designs. LiteX stays outside the
  repository: `litex/README.md` says how to install it.
- Run a job that uses much CPU time at the lowest priority (`nice -n 19`). The `build.sh` scripts
  do this themselves.
- Do not add automated tests unless asked. Validate a change on the board or in the simulation, and
  report what was checked.
- Comments explain intent, invariants and causes. They do not repeat the statement below them.

## Language and style

Project files are in English: documents, comments and script output. Keep signal names, part
markings and quoted text as they are. Communication with the user need not be English.

Write documents in simple technical English. The model is ASD-STE100 (Simplified Technical
English), applied at about 80%: its writing rules apply, but its dictionary of approved words does
not.

- One sentence has one statement or one instruction. A sentence that describes has a maximum of 25
  words. A sentence that gives a step has a maximum of 20 words.
- Use the active voice. Name the subject: the board, the design, the workbench, the host or the
  card.
- Use the present tense for what is true of the board. Use the past tense for a measurement or an
  event, and give its date.
- One word has one meaning, and one meaning has one word. Do not use a different word for the same
  thing.
- Put the condition first: "If ..., the design ...". Use a list for two or more conditions or
  steps.
- Do not put more than three nouns together.
- One paragraph has one topic and a maximum of six sentences.
- Do not use metaphors, idioms or Latin abbreviations.
- Technical names stay as they are: signal names, pin names, register values and command names. A
  table cell can contain a phrase that is not a full sentence.
